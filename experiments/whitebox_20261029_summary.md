# B：白盒 200 题单轮实验与下一轮候选

本轮已完成一次真实模型全量开发测试：**448.9/1000，答案完全正确 116/200（58%）**。去掉时延罚分后的诊断分为 614.9，实际时延罚分合计 166。结果说明环境和整体链路已经跑通，但准确性与时延都还需要改进；这不是正式比赛成绩，也不能证明此前 B 的改动优于原始基线。

下一轮只处理“SQL 精调丢失模板输出列”。在冻结本轮模型输出的离线回放中，候选规则改善 25 题、退化 0 题，不含时延的诊断分合计增加 80.4。该结果只支持继续验证候选，不能替代真实模型复测。候选开关默认关闭。

## 4. 单因素候选：保留模板输出列

本轮 49 题的 SQL 在精调后发生变化。使用记录中的 API 条件与填参结果，调用原执行器和原评分器，分别重放精调 SQL 与模板原 SQL，**49/49 个实际 SQL 的无时延得分与原记录一致**。

具体例子：CMDB-019 的模板输出 `name, createdAt`，精调只剩 `createdAt`；CMDB-020 丢了 vcpuSize/ramSize/diskSize；CMDB-248 丢了 module_name。案例编号只用于实验说明，不进入运行时判断。

候选规则在 `implementation/runbook_matcher.py`：

1. 保留现有 SQL 精调与合法性检查。
2. 只有原/精调 SQL 的 GROUP BY 文本与聚合函数种类签名一致时，才比较输出列名。
3. 在 schema 空表上准备查询，读取输出列名；模板列缺失时回退所选模板原 SQL。允许添加列；未知 schema 或无法确定原输出列时不猜测；分组/聚合结构变化时不应用这项新规则。
4. 通过 `RUNBOOK_PRESERVE_TEMPLATE_COLUMNS=1` 显式启用，默认 `0`；记录触发原因、前后列名和缺失列。

| 冻结输出回放指标 | 结果 |
|---|---:|
| SQL 变化题数 / 得分重现一致 | 49 / 49 |
| 新规则触发 | 30 |
| 相对精调 SQL 改善 / 退化 | 25 / 0 |
| 无时延诊断分差合计 | +80.4 |
| 新增模型请求 | 0 |

这不是候选真实模型成绩：模型响应、选择和参数全部固定；回退整条原 SQL 可能同时撤回其他 SQL 修改，不能将全部差值因果归于单一列删除；它也可能阻止未来合法的减列/改别名。当前规则是保守的实验假设，不是通用语义解析器。真实查询的列准备开销与时延影响尚未测量。

迁移辅助函数到实际 matcher 后，49/49 个离线策略决策保持一致。40 项本地测试全部通过，无跳过，模型通信使用 mock；新增边界涵盖：开关开/关、允许增列、允许分组变化、原投影未知时不强制回退。真实本地数据服务参与了原执行/评分链路测试，不能将 mock 测试分数当作模型表现。

### 已获准的 6 题真实候选复测

用户批准后按预登记顺序执行一次，源码提交 `9baccb0`，单因素为 `RUNBOOK_PRESERVE_TEMPLATE_COLUMNS=1`，其他生成设置与全量基线一致，模型请求硬上限 18。实际 15 请求、0 失败，墙钟 21.890s，评估进程峰值 253.34 MiB。该进程只执行 6 题，不能与 200 题进程峰值作节省内存比较。

|---|---|---|---|
| CMDB-001，正确控制 | 5 → 5 | 5 → 5 | 否，输出列保留 |
| CMDB-004，正确控制 | 5 → 4 | 5 → 5 | 否，本次 4.08s 扣 1 |

5 个作答题均完全正确；第 6 题仍拒答，因此不能称 6/6 答案正确。6 题选中模板与基线相同，三个目标案例的日志都记录了新模型输出缺列、新规则触发和原 SQL 回退。该证据支持机制确实在真实链路中执行；网络时延、服务状态及新生成响应没有被配对控制，不能把总分差或耗时变化全部作因果归因。

预登记计划中 CMDB-004 的人工标签“详情控制”误填，按实际参考 SQL 应属状态分组；本次题号、顺序、配置没有更换。历史计划文件保持原样，实际判断以 SQL 和日志为准。

**候选判断：保留实验开关、继续扩大回归，暂不默认启用。** 该诊断组有明确开发选择偏差，即使目标案例通过也需要更广回归，不能称作未见题泛化验证。全量 200 题只测试了关闭新开关的版本；没有将候选的 6 题分数替换进全量基线。

## 6. 复现与交接

从 B 目录运行，先按 README 准备环境、启动本地服务。下面分析命令不调用模型，输出文件使用新名称，避免覆盖历史记录：

```bash
.venv/bin/python analyze_whitebox.py experiments/whitebox_20261029_full.jsonl \
  --output reports/recomputed_analysis.json
.venv/bin/python replay_sql.py experiments/whitebox_20261029_full.jsonl \
  --output reports/recomputed_sql_replay.jsonl
RUNBOOK_TEST_LOCAL_API=1 .venv/bin/python -W error::ResourceWarning \
  -m unittest discover -s tests -q
```

完整真实测试历史命令如下，**它会再次调用模型，不属于免费复现；需要新的当轮授权**：

```bash
.venv/bin/python run_whitebox.py --run --limit 200 --max-requests 600 \
  --spent-requests 65 --max-output-tokens 1024 \
  --output experiments/whitebox_20261029_full.jsonl
```

上述历史输出已存在，入口会拒绝覆盖。准确复现基线还需使用记录中的源码版本及默认关闭的候选开关，不能把最新候选代码误当已测全量版本。

候选固定六题的脚本也默认只预检：`.venv/bin/python experiments/run_projection_20261029.py`。已获准的那次使用 `--run`；历史输出已存在，脚本会拒绝覆盖。复测或扩大范围需要新预算，不能重复使用历史授权。

交接给 A/C：运行时只迁移 B 自有 matcher/system 的必要差异，不用整个 B/implementation 覆盖团队代码；诊断工具、记录与锁定依赖供 C 复核。A 的模板与 BM25、C 的评估入口及所有受保护文件未修改。

后续顺序：先验证本轮输出列候选；再单独分析资源门禁是否遗漏 API 资源；随后处理参数/API 条件和模型调用时延。每次只改一个主要因素，同题对照保留原评分，正式模型和黑盒就绪后另行验证。多模板组合等待 A/C 明确模板与结果合同。
