## 为什么只放行一题

API 里出现某种资源，不能单独证明模板能回答关于它的问题。例如有的模板加载多种资源，但最终 SQL 只统计其中一种；另有“节点类型是虚拟机还是物理机”“存储池的磁盘类型”等属性词触发资源词门禁。这些需要单独核验语义和输出能力，本轮不一并放宽。

| 审计结论 | 数量 / 处理 |
|---|---|
| 原资源门禁拒答 | 27 |
| 新规则具有直接查找覆盖证明 | 1，进入填参及源记录验证 |
| 其余原资源拒答 | 26，保持拒答；不把它们全部称为合理弃权或误拒 |
| 200 个固定选择中的门禁判断不变 | 199 |

这是在旧模型选择固定的条件下比较资源门禁；没有重新生成 200 题的模型响应，也没有得出新的全量成绩。审计早期发现大小写归一遗漏会误放行“弹性IP”，已在提交前修正，并补混合大小写反例。

## 修复的实际行为

`runbook_matcher.py` 保持原有资源词集合与门禁行为，只补充以下路径：

1. 首步 API 有过滤条件；下一步 API 的表确实出现在 SQL 中，且不会被后续同名表覆盖。
2. 下一步条件明确引用 `{{字段 from step 1}}`；源字段和目标条件字段都存在于当前 schema，且这对字段出现在原有 JOIN_RELATIONS 关联清单中。字段都存在但互不关联也不能放行。
3. 不把 resources 声明、无依赖的独立 API、未过滤来源、未知字段、错误步骤号或任意多步路径当作覆盖证明。
4. 参数和显式 API 条件检查通过后，用原执行器的 `_execute_single_api_call()` 查询首步，确认依赖字段确有非空值；缺失时以 `invalid_resource_lookup` 拒答，停止精调和最终执行。
5. 验证通过才继续原 SQL 精调及 `execute()`。第一次查找使用原执行器缓存，正常执行时复用相同查找结果；未改写执行器或新建执行框架。

原执行器在前一步没有可用依赖值时可能省略下一步条件，扩大查询。本轮为新增放行路径增加源记录核验，避免引入这种退化；**未全面重写或修复所有既有多步模板的执行边界**。

诊断新增 `resource_coverage` 和 `resource_lookup`，记录覆盖缺口、证明、验证结果、行数与耗时，不记录源记录的 id。资源检查不读取 case_id、参考答案或问题查找表。

复用原执行器内部函数是一项版本耦合：当前固定执行器的 SHA-256 由只读 manifest 保护。A/B/C 整合时需保留该版本与缓存语义，不能假设未核验的新执行器具有相同内部接口。原数据 API 层可能把请求失败返回为空列表，因此“空记录/缺失依赖”诊断本身不能证明实体不存在；如果函数实际抛出异常则继续传播。
