下一训练失败的API把“运行中虚拟机”状态槽错误绑定到第二次HOST请求，原映射因此拒绝填值。新增窄范围纠正：仅当两个HOST请求的region/AZ占位合同一致、原SQL具有已证HOST.id=VM.hostId JOIN、两个CI均有相关字段、题文明示运行中VM列表且无否定/OR/额外不支持条件时，将第二步CI更正为VM_NOVA。原SQL、两个请求的全部范围条件保持原样；固定默认范围、具名额外实体、未证JOIN和额外筛选不进入此修复。

同例由拒答恢复4.8/5，最终合并源码复核仍4.8/5。原生审计发现：原参考API只在HOST上筛normal，VM未筛状态；其输出与保存答案逐行完全一致，共1335个不同VM，其中active1287、stopped48。按题文明示运行中VM返回1287个，参考裁定待C/主办方；没有混入stopped或修改评分器。原生字段复核还确认GaussDB/ELB没有azoneName，未猜字段补条件。

最初6题回归30/30；追加2题回归4/10的失败完整保留。日志证明该失败没有触发状态角色修复，原因是模型将SUM(vCPU)变为SUM(DISTINCT vCPU)。新增既有SUM/AVG输出列的DISTINCT方式保护，沿用已有PRESERVE_AGGREGATE_GRAIN开关；可以追加独立统计列，原COUNT合同和关闭开关政策保留。合成数据8/8/16证明正常和32、数值去重和24；此前真实错误提案的免费合同回放确定被拒绝，新实际同例5/5（这次新提案未改DISTINCT），6题回归30/30。

该保护不认证旧模板业务正确性：同一训练范围、同一HOST域的3个集群分组中，原JOIN行求和403872、SUM(DISTINCT数值)768、按HOST身份各算一次6072；三个分组的HOST数量相同。JOIN倍增及参考计量口径需独立业务核查，不能把原评分5当成总vCPU计算已正确。
